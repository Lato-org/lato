# AGENTS

## Project overview

Lato is ecosystem of Rails engines for building admin panels with authentication, user management, Bootstrap UI, reusable components, operations, settings, storage, spaces, and CMS features.

`lato` is base Rails engine. Other Lato gems extend it with specific modules.

## Gem purpose

`lato` provides core admin panel infrastructure:

- Authentication and account management.
- Optional verification and authentication methods.
- Bootstrap layout, navbar, sidebar, and overridable partials.
- UI components for forms, index tables, actions, and data rendering.
- Operations system for visual background job execution.
- Shared models such as users, sessions, invitations, and operations.

## Documentation

- Source of truth: documentation views in dummy app `test/dummy/app/views/tutorial/` (e.g. `configuration.html.erb`). Edit these, never the `docs/` output.
- `docs/*.html`, `docs/documentation.txt`, `docs/SKILL.md` are GENERATED by `bin/generate_docs.rb` — do not edit by hand, they get overwritten.
- Regenerate after editing source views: dev stack running, then `ruby bin/generate_docs.rb`.
- Public behavior changes (e.g. new `Lato::Config` option) must update the matching source view under `test/dummy/app/views/tutorial/`, then regenerate docs.
- `test/dummy/app/views/tutorial/` is the documentation source for this base gem; extension gems use `application/documentation.html.erb`.
- Extension gems must keep `test/dummy/app/views/application/documentation.html.erb` updated with user-facing documentation for installation and usage.

## Local setup

- Ruby via `rbenv`.
- Install gems: `bundle`.
- Migrate dummy DB: `rails db:migrate`.
- Seed dummy DB: `rails db:seed`.
- Start dev stack: `foreman start -f Procfile.dev`.

## Main commands

- Run tests: `bin/rails test`.
- Generate docs: `ruby bin/generate_docs.rb`.
- Publish gem: `ruby ./bin/publish.rb`.

## Agent notes

- Use double quoted Ruby strings in new files; match surrounding style when editing existing files (much of the engine uses single quotes).
- Do not add implementation details to user documentation unless needed for usage.
- Keep generated docs aligned with actual views and public APIs.

## Security conventions

- Escape user data in helpers and partials; mark strings `html_safe` only when they never contain user input.
- In Stimulus controllers never use `innerHTML` with attribute or message data: use `textContent` or DOM APIs.
- No inline `<script>` or inline event handlers (`onclick=...`) in engine views: put behaviour in Stimulus controllers so host apps can use a CSP without `'unsafe-inline'` for scripts.
- Vendor new third-party JavaScript under `app/assets/javascripts/lato/vendor` and pin it in `config/importmap.rb` instead of loading it from a CDN at runtime.
- Rate limits and verification codes rely on a shared `Rails.cache`: do not assume a per-process cache.
- Add tests for every security fix.

## Security release baseline

- Rails 8.1.3.1 or newer in the 8.1 series is required.
- Run `ruby bin/publish.rb` from a named release branch after tests pass. It builds the exact version, commits changes, tags that commit, publishes to RubyGems, and pushes the branch and tag.
- Applications using Active Storage with vips require libvips 8.13 or newer.
