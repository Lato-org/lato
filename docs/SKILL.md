# Lato Rails Gem

Lato is a Rails engine that provides a fully-featured admin panel with authentication, responsive UI (Bootstrap), background job operations, invitation system, and rich UI components ready to use with Rails >= 8.1.3.1 and < 8.2.

## Tutorial
Tutorial Tutorial Getting Started To create custom presentation pages for your project, you can modify the ApplicationController by extending the Lato::ApplicationController class and specifying the use of Lato's layout: class ApplicationController < Lato::ApplicationController layout 'lato/application' def index; end end How to Hide the Sidebar To hide the sidebar, you can use one of the methods provided by the Lato::Layoutable concern (already included via Lato::ApplicationController): class ApplicationController < Lato::ApplicationController layout 'lato/application' def index hide_sidebar end end To apply this rule to all controller actions, you can quickly use before_action: class ApplicationController < Lato::ApplicationController layout 'lato/application' before_action :hide_sidebar def index; end def other_action; end end How to Use Custom CSS and Customize Bootstrap To customize Lato's CSS, you can modify your main application's application.scss file: @import url('https://fonts.googleapis.com/css2?family=Lato:ital,wght@0,100;0,300;0,400;0,700;0,900;1,100;1,300;1,400;1,700;1,900&display=swap'); // Override bootstrap variables $font-family-base: 'Lato' !default; $primary: #03256C; // Import Lato CSS @import 'lato/application'; // Add custom CSS pre { border-radius: 15px; } How to Use Custom Stimulus JS Controllers Stimulus JS is a dependency of Lato and can be used normally without specific integrations. Notes All controllers handled by Lato are named, by definition, lato_name_controller.js. Example: lato_hello_controller.js is used with the attribute data-controller="lato-hello". How to Protect a Page To authenticate a page and prevent public access by unauthenticated users, you can use one of the methods provided by the Lato::Sessionable concern (already included via Lato::ApplicationController): class TutorialController < ApplicationController def index return unless authenticate_session end end To apply the rule to all actions in the controller, you can simply use before_action: class TutorialController < ApplicationController before_action :authenticate_session def index; end end Notes Just like authenticate_session, you can also use its opposite not_authenticate_session to hide a page from authenticated users. Example: class AuthenticationController < ApplicationController before_action :not_authenticate_session, only: %i[signin] before_action :authenticate_session, only: %i[signout] def signin; end def signout; end end Limiting the Number of Requests To limit the number of requests to a page, you can use the limit_requests method: class TutorialController < ApplicationController before_action :authenticate_session before_action :limit_requests, only: %i[index] def index; end end The limit_requests method accepts two parameters: limit (default: 10) and time_window (default: 10.minutes). These parameters define the maximum number of requests allowed per client IP and action within the time window: exactly limit requests pass, the next one receives an HTTP 429 response (message lato.too_many_requests). Counters use Rails.cache.increment, so the limit requires a persistent cache shared across processes (Redis, Solid Cache, Memcached). See the configuration page. Accessing the Logged-in User The user currently logged into Lato is always accessible in all controllers and views through the @session instance of the Lato::Session model: class TutorialController < ApplicationController # ... def index @user_id = @session.user_id @user = @session.user.first_name end # ... end Notes Using @session.user_id instead of @session.user.id avoids loading the user from the users table. Session validity is still checked with a query on lato_session_records. @session.valid? lets you check whether the user is logged in or not. Programmatic Session Management The Lato::Sessionable concern also provides methods to programmatically create and destroy sessions, useful for custom authentication flows or testing: class CustomController < ApplicationController def custom_login user = Lato::User.find_by(email: params[:email]) return head :unauthorized unless user&.authenticate(params[:password]) # Create a session for the user session_create(user.id) end def custom_logout # Destroy the current session session_destroy end end Notes session_create(user_id) creates the Lato::SessionRecord database row, calls reset_session, sets the encrypted session cookie and refreshes the @session instance. session_destroy revokes the Lato::SessionRecord row, calls reset_session and clears the session cookie. Never create a session from an unauthenticated identifier such as an email alone: always verify the credentials first. Both methods are provided by the Lato::Sessionable concern. Engine Routes The engine exposes the following public routes (use them with the mount prefix helper, e.g. lato.account_path): Helper Description lato.root_path Engine root lato.authentication_signin_path Signin page lato.authentication_signup_path Signup page lato.authentication_recover_password_path Password recovery page lato.authentication_accept_invitation_path Invitation acceptance page lato.account_path Account management page lato.operation_path(id) Operation detail page lato.switch_locale_path(locale:) Change locale (POST) lato.operations_show_path(id) Deprecated legacy route, use operation_path lato.switch_locale_get_path(locale:) Deprecated: changes state via GET, use the POST switch_locale_path


## Configuration
Tutorial Configuration Configuration Lato's configuration is managed by the Lato::Config class and can be customized through a dedicated initializer. To override the default settings, create an initializer and add the following code: Lato.configure do |config| config.application_title = 'Lato example app' config.session_root_path = :tutorial_path end Application Configuration Lato.configure do |config| config.application_title = 'Lato example app' # Application title config.application_version = '1.0.0' # Application version (default: '1.0.0') config.application_company_name = 'Lato Team' # Name of the owning company config.application_company_url = 'http://domain.com' # URL of the owning company config.application_brand_color = '#03256c' # Primary brand color used in navbar and UI elements (default: '#03256c') end Authentication Configuration Lato.configure do |config| config.auth_disable_signup = true # Disable user self-signup config.auth_disable_recover_password = true # Disable password recovery config.auth_disable_web3 = true # Disable Web3 wallet login config.auth_disable_authenticator = true # Disable Google Authenticator login config.auth_disable_webauthn = true # Disable WebAuthn login config.auth_disable_signin_success_mail = true # Disable login notification email config.auth_recover_password_hourly_limit = 100 # Max password recovery emails sent per hour across all users, nil to disable (default: 100) config.auth_password_min_length = 8 # Minimum password length (default: 8) end auth_password_min_length is validated whenever a password is set (signup, invitation, password recovery and password change), and the signup and password forms display the requirement. HCaptcha Configuration HCaptcha is a service that helps protect websites from spam and abuse by using advanced risk analysis techniques. By integrating HCaptcha into your application, you can add an extra layer of security to authentication forms. When configured, it protects the signup and password recovery forms. Lato.configure do |config| config.hcaptcha_site_key = 'your-hcaptcha-site-key' config.hcaptcha_secret = 'your-hcaptcha-secret' end Requests Limit and Reverse Proxy Authentication actions (signin, web3 signin, signup, password recovery, email verification, second factor) are limited per client IP and action. By default limit_requests(limit = 10, time_window = 10.minutes) allows exactly 10 requests per IP and action in each window; the 11th request receives an HTTP 429 response (message lato.too_many_requests). Signin also has a per-account limit: after 10 failed attempts in 15 minutes the email is blocked, from any IP, until the window passes. A successful signin resets the counter. Second factor (authenticator and WebAuthn) attempts are counted per user as well. Trade-off: an attacker who knows an email address can temporarily lock that account out of signin. Shared cache required Rate limits, password recovery codes, email verification codes and semaphores are stored in Rails.cache. Use a persistent cache shared across processes (Redis, Solid Cache, Memcached). With :null_store rate limits are disabled and password recovery never works; with :memory_store and multiple processes limits are per process. In production Lato logs a warning at boot if Rails.cache is a NullStore. The client IP is read from request.remote_ip, so the application should run behind a reverse proxy (e.g. nginx, Kamal proxy, a load balancer) that appends the real client IP to the X-Forwarded-For header. Proxies on private networks are trusted by default; if your proxy uses a public IP, add it to the trusted proxies: # config/application.rb config.action_dispatch.trusted_proxies = ActionDispatch::RemoteIp::TRUSTED_PROXIES + [IPAddr.new('203.0.113.10')] Assets Configuration Lato.configure do |config| config.assets_stylesheet_entry = 'application' # CSS file for Lato styling (default: application.scss) config.assets_importmap_entry = 'application' # JS entry point for Lato (default: application.js) end Session Management Configuration Lato.configure do |config| config.session_lifetime = 5.days # Absolute lifetime of the session cookie and of the session database record (default: 30 days) config.session_root_path = :tutorial_path # Path to redirect users after login/signup end session_lifetime is an absolute lifetime: it is not renewed on activity and there is no idle timeout. The session cookie is httponly, same_site: :lax, and secure only when the request is SSL, so set config.force_ssl = true in production. Lato 3.25 requires Rails >= 8.1.3.1 and < 8.2. On upgrade, run rails lato:install:migrations and rails db:migrate before serving requests. Existing session cookies require a fresh sign-in. Sessions use revocable database tokens. Signout revokes the current device. Password changes and recovery revoke every device; password recovery preserves existing second factors. Sensitive account changes require the current password and an enrolled second factor. Authenticator enrollment requires a valid code before activation. Active authenticator secrets are not displayed. Enrollment continuations expire after five minutes. Extensions must use session_update(extra_params) when changing session attributes so revocation and secure cookie options remain intact. Email Configuration Lato.configure do |config| config.email_from = 'demo@mail.com' # Sender email address for notifications end Note The email_from setting can include a display name using the format "Name" <example@domain.com>. Example: Lato.configure do |config| config.email_from = '"Company name" <demo@mail.com>' end Legal Information Configuration Lato.configure do |config| config.legal_privacy_policy_url = 'https://domain.com/privacy' # Privacy policy URL config.legal_privacy_policy_version = 32 # Version number of the active privacy policy config.legal_terms_and_conditions_url = 'https://domain.com/terms' # Terms and conditions URL config.legal_terms_and_conditions_version = 32 # Version number of the active terms and conditions end Note Lato tracks which version of the privacy policy and terms the user has accepted. If the logged-in user has accepted a version lower than the one configured via legal_privacy_policy_version or legal_terms_and_conditions_version, a prompt will appear in the account management page to accept the new policies. To check whether a user has accepted the latest policy versions, use the valid_accepted_privacy_policy_version? and valid_accepted_terms_and_conditions_version? methods on instances of the Lato::User model. Example: user = Lato::User.all.first throw "Privacy policy not accepted" unless user.valid_accepted_privacy_policy_version? throw "Terms and conditions not accepted" unless user.valid_accepted_terms_and_conditions_version? Account Connection Configuration Lato.configure do |config| config.web3_connection = true # Allow users to link a Web3 wallet to their account config.authenticator_connection = true # Allow users to link Google Authenticator to their account config.webauthn_connection = true # Allow users to link WebAuthn to their account config.webauthn_origin = 'http://localhost:3000' # Origin URL for WebAuthn (must match the one used in your app) config.webauthn_rp_name = 'Lato Example App' # Relying Party name for WebAuthn end WebAuthn webauthn_origin accepts a string or an array of origins. In production use HTTPS origins; the relying party id is derived from the origin. Lato.configure do |config| config.webauthn_origin = ['https://app.example.com', 'https://www.example.com'] end The signature counter is persisted and a non-increasing counter is rejected to detect cloned authenticators. Limitations: each user can register one credential, there are no backup codes, and user verification is not required. Authenticator (TOTP) A code can be used only once (replay protection) and a drift of 15 seconds behind is accepted. The pending second factor step after the password expires after 10 minutes and is dropped after 5 wrong codes; the user must sign in again. The authenticator secret is stored in clear in the database, consider Active Record encryption for production. Web3 Web3 requires the host application to add gem "eth" to its Gemfile; it is not a runtime dependency of Lato. The signed message is a text bound to host, purpose, nonce and issue time: example.com wants you to sign in with your Ethereum account. URI: https://example.com Nonce: ... Issued At: ... The nonce is single use and expires after 5 minutes. This is not a full SIWE (EIP-4361) implementation. Web3 signin pages require the user to be signed out. The browser loads ethers 5.7.2 from cdnjs with a dynamic import(): the version is pinned but without Subresource Integrity (import() cannot carry an integrity attribute). Applications that need strict supply-chain control should vendor the library. Security Web3 and email verification views use inline scripts, so a Content Security Policy needs unsafe-inline or nonces for those pages. See the "Production security checklist" in the README for the full list (force SSL, shared cache, session lifetime, cleaner jobs, invitations, secrets at rest).


## Customization
Tutorial Customization Customization Lato can be customized in several ways: Configure Bootstrap layout classes using the Lato::Btstrap class; Customize layout behavior via the Lato::Layoutable concern; Update layout content using content partials; Modify page-specific CSS using body classes. Layout Class Configuration With the Lato::Btstrap class, you can customize the Bootstrap classes used by Lato for the layout’s UI components. The layout is composed of the following UI elements: navbar, content, sidebar, and footer. To override the default classes, you can create an initializer with the following code: Lato.bootstrap do |btstrap| btstrap.navbar = 'navbar-light navbar-expand-lg fixed-top bg-light shadow-sm px-3' btstrap.navbar_container = 'container-fluid' btstrap.navbar_collapse = 'justify-content-end' btstrap.sidebar = 'sidebar' btstrap.content = 'p-3' btstrap.content_container = 'container-fluid' btstrap.footer = 'bg-light px-3 py-2' btstrap.footer_container = 'container-fluid' end Layout Behavior Customization Lato’s layout behavior can be customized using methods provided by the Lato::Layoutable concern. This concern offers a set of useful functions. Here’s an example: class TutorialController < ApplicationController def index hide_sidebar # hides the sidebar show_sidebar # shows the sidebar active_sidebar(:tutorial) # sets active state on sidebar item with key :tutorial active_navbar(:tutorial) # sets active state on navbar item with key :tutorial page_title('Custom title') # sets the page title page_class('custom-class') # adds a CSS class to the body element page_classes(%w[class-one class-two]) # replaces all body classes with the given array end end Note All Lato::Layoutable methods can also be used inside controller before_action callbacks. Layout Content Customization Most layout content in Lato is defined via specific partials following the naming convention _partial-name_content.html.erb. ## Operations
Tutorial Operations Operations Operations are Lato's system for visually managing the execution of background Jobs. Operations are handled by several components: The Lato::Operation model initializes all operations and tracks their execution state. The Lato::OperationsController controller manages user access to an ongoing operation. The lato_operation component allows displaying the operation status in the front-end. Converting a Job into an Operation The easiest way to convert a Job into an operation is to simply make the Job a subclass of Lato::ApplicationJob. Additionally, the perform() method must accept a single Hash parameter called params. Only classes inheriting from Lato::ApplicationJob can be started as operations: Lato::Operation#start ignores any other class. # Before class MyJob < ApplicationJob def perform(hello) puts hello end end # After class MyJob < Lato::ApplicationJob def perform(params = {}) puts params['hello'] end end Generating an Operation Operations can be generated using the generate method of the Lato::Operation model. Creating an operation requires three parameters: the name of the job to execute, a Hash of parameters to pass, and the ID of the user requesting the operation. operation = Lato::Operation.generate('ExportProductsJob', { product_ids: [1, 2, 3] }, @session.user_id) Once generated, the operation must be started using the start method. Here is an example controller that starts an operation: class CustomController < ApplicationController def create_operation_action @operation = Lato::Operation.generate('OperationExampleJob', {}, @session.user_id) respond_to do |format| if @operation.start format.html { redirect_to lato.operation_path(@operation) } format.json { render json: @operation } else format.html { render :index, status: :unprocessable_entity } format.json { render json: @operation.errors, status: :unprocessable_entity } end end end end Displaying the Outcome of an Operation Each operation can be viewed at the route lato.operation_path(operation_id). To ensure data security, an operation is only accessible to the user who initiated it. Each operation can have four states: created, running, completed, failed. The operation view, handled via the lato_operation component, shows the real-time status and output of the operation. Use the link below to try out an operation: <%= link_to 'Generate Operation', main_app.custom_create_operation_action_path, data: { turbo_method: :post } %> Notes To display the result of an operation directly in-page, you can use lato_action_controller features. These functions can also be called even if the Job is executed without using the Lato::Operation model. ## Module: Lato Users
Modules Lato Users Lato Users How to use Lato Users lato_users adds a user management section to a Lato admin panel. Use it when the application needs admins to create users, edit user data, manage invitations, and handle account verification from the back office. Installation Requires Rails 8.1.3.1 or newer in the 8.1 series and Lato 3.25.0 or newer. Existing applications must run rails lato:install:migrations (Lato session records) and rails db:migrate before deployment. Previous sessions are invalidated. The host application also needs a configured Action Mailer (verification and invitation emails) and a working Rails.cache store (email semaphores and verification codes). Password parameters must be filtered from logs (config.filter_parameters including :passw). Add Lato Users to the application Gemfile: gem "lato" gem "lato_users" Install the gem and its migration (adds the lato_users_admin column). rails lato_users:install:application is a no-op and is not required: bundle rails lato_users:install:migrations rails db:migrate Mount the engine in config/routes.rb: Rails.application.routes.draw do mount LatoUsers::Engine => "/lato-users" # ... end Import styles in app/assets/stylesheets/application.scss: @import "lato_users/application"; Import JavaScript in app/javascript/application.js: import "lato_users/application" Add the menu entry, visible only to admins (the engine activates :lato_users on its pages): <% if @session.user&.lato_users_admin %> <%= lato_navbar_nav_item :lato_users, lato_users.root_path do %>Users<% end %> <% end %> Routes under the mount path: / (redirects to users), users (with resend_verification_email, manual_verify_email, revoke_email_verification, force_update_password) and invitations (with resend). Permissions Users must be logged into Lato and must have Lato Users admin permission enabled. Grant permission from application seeds or from an existing admin account. user = Lato::User.find_by(email: "admin@example.com") user.update!(lato_users_admin: true) lato_users_admin is effectively a super-admin permission: it can grant any other engine's admin permission (lato_settings_admin, lato_spaces_admin, lato_storage_admin, lato_cms_admin_role, ...) to any user. Admins cannot remove their own lato_users_admin, and the last users admin can be neither demoted nor deleted. Non-admin requests are redirected to the Lato root (403 for non-HTML formats). Admin permissions in the user form The user form loads the available admin permissions automatically. Each Lato engine (for example lato_users, lato_spaces, lato_cms) adds its own permission column to the shared Lato::User table, and the form discovers them by naming convention: lato_*_admin — a boolean column, rendered as a checkbox (on/off permission). lato_*_admin_role — an integer column, rendered as a select (a role with multiple levels). No configuration is required in lato_users: install an engine that adds one of these columns and its control appears in the form and gets permitted on create/update. Its label is taken from the activerecord.attributes.lato/user.<column> translation (provided by this gem for the official engines, otherwise add it yourself). Role permissions (enum) For a role column, the owning engine provides the selectable options (label and value) by defining a Lato::User.<column>_options class method that returns [[label, value], ...]. lato_users calls it to build the select and rejects submitted values that are not in the options. For instance, lato_cms exposes its roles through Lato::User.lato_cms_admin_role_options, so the CMS role appears as a dropdown with the roles configured by that engine. You can define your own role permission the same way, either from an engine or directly in the application. The example below adds a lato_shop_admin_role with three levels. 1. Add the integer column to the shared lato_users table: # db/migrate/xxxxxxxxxxxxxx_add_shop_admin_role_to_lato_user.rb class AddShopAdminRoleToLatoUser < ActiveRecord::Migration[8.1] def change add_column :lato_users, :lato_shop_admin_role, :integer, default: 0, null: false end end 2. Expose the options by reopening Lato::User and defining lato_shop_admin_role_options. Wrap it in to_prepare so it survives code reloading in development. The method must return an array of [label, value] pairs, and the values must match the integers stored in the column: # config/initializers/lato_shop_roles.rb Rails.application.config.to_prepare do Lato::User.class_eval do def self.lato_shop_admin_role_options [ [I18n.t("shop.roles.none"), 0], [I18n.t("shop.roles.manager"), 1], [I18n.t("shop.roles.owner"), 2] ] end end end 3. Add the labels to a locale file. The option labels come from the keys used above, and the field label of the select comes from the Lato::User attribute translation: # config/locales/en.yml en: shop: roles: none: No access manager: Manager owner: Owner activerecord: attributes: lato/user: lato_shop_admin_role: Shop role That is all. After running the migration the new role appears automatically as a select in the user form, gets permitted on create and update, and its value is saved on the user record. No change to lato_users is required. Reading the role back is a plain integer comparison: user.lato_shop_admin_role # => 0, 1 or 2 user.lato_shop_admin_role >= 1 # true when the user is at least a manager Keep 0 as the "no access" value: the form and permission checks treat any value greater than zero as a granted role, mirroring how boolean permissions work. What admins can do View all application users. Create new users. Edit user email, name, and available Lato admin permissions. Changing the email of another user revokes that user's sessions. Verify or revoke email verification. Send a new verification email. Set a password when creating a user, or force a new random password later. It is shown once in the response, never stored in flash or session, and all the user sessions are revoked. Delete users when allowed by the application data constraints. Create, resend and delete invitations. Admins cannot delete their own currently logged-in account from Lato Users. Users created by an admin are saved with the current privacy policy and terms versions, because Lato::User requires them. Passwords cannot be changed from the edit form. There is no audit log of admin actions. Recommended setup Create at least one administrator in seeds and enable lato_users_admin. This guarantees access to the user management panel after first deployment. admin = Lato::User.find_or_create_by!(email: "admin@example.com") do |user| user.first_name = "Admin" user.last_name = "User" user.password = "Password1!" user.password_confirmation = "Password1!" user.email_verified_at = Time.current end admin.update!(lato_users_admin: true) Invitations Use invitations when users should not self-register. Admins can create invitations from the Lato Users panel. Invited people receive an email and complete account creation from the invitation link. Accepted invitations cannot be deleted, emails already registered are rejected, and Lato limits sending to one email every 2 minutes per invitation. If delivery fails the invitation is kept and the panel says so: use Resend to try again.

Media library file, image, video, and gallery fields don't upload straight into the field: admins pick from a shared Media library (Media in the sidebar), scoped to the current Lato Spaces group like pages. Each field opens a picker overlay to search the existing library or drag & drop a new file; the same media item can be reused across any number of fields and pages. A media item's name, alt text and title are edited from the library's own edit form, not from the upload dialog — on upload, name defaults to the filename. Uploads are checked on the server against media_allowed_content_types and media_max_file_size (see Configuration). Deleting a media item still referenced by a field is refused until it's removed from every field using it. An admin can force the deletion (the delete endpoint accepts force=true): the media is then removed from every field that used it. Uploads (from the library and from the picker's Upload new tab alike) show a progress bar with the real upload percentage, so large videos don't look like a frozen page. Where a media item is used The library index shows how many page fields reference each media item, and filters list only the unused ones (the only ones that can be deleted without force) or those still missing an alt text or a title in at least one configured locale (alt text only applies to images; a title is editable on any media type). Each media item also has a detail page: a read-only summary (preview, name, alt text and title per locale) plus the list of pages using it, with a link to each one and the fields involved. Replacing a file The edit form of a media item has a second tab, Replace file (admins only): it uploads a new file over the existing media item, keeping the same record, so every page and field already referencing it shows the new file. That's the point of the action — swapping a logo everywhere at once — and its danger, which is why the form states how many fields are affected and asks for a confirmation. The previous file is deleted, and media_type is re-inferred from the new one. Metadata (name, alt text, title) is kept: to change it, use the Details tab. Uploading a file from the library's Upload action, as before, always creates a separate media item instead. Alt text and title are translatable: alt text is only shown for image media, title for every media type, and the edit form has one tab per locale configured in LatoCms.config.locales for each. Each locale's text is independent — leaving one blank doesn't affect the others. image = LatoCms::Media.find(12) image.alt_text(:en) # => "A dog running on the beach" image.alt_text(:it) # => nil, if the Italian tab was left blank image.alt_text_translations # => { "en" => "A dog running on the beach" } image.title(:en) # => "Dog on the beach" image.title_translations # => { "en" => "Dog on the beach", "it" => "Cane in spiaggia" } image.alt_text / image.title without an explicit locale resolve against I18n.locale. When a media item is read off a page's field (page_field.attachments in the JSON API, as alt_text and title), both resolve against that page's own locale instead, so a multi-locale API response always gets the right language regardless of the server's current I18n.locale. AI-generated alt text and title Configure an OpenAI-compatible endpoint to have alt text and title generated automatically: LatoCms.configure do |config| config.llm_api_url = "https://api.openai.com/v1" config.llm_model = "gpt-4o-mini" config.llm_api_key = Rails.application.credentials.dig(:openai, :api_key) # Optional, both default to true once the LLM is configured config.llm_generate_alt_text = true config.llm_generate_title = false # Optional custom prompts (nil = built-in defaults, see LatoCms::Config::DEFAULT_LLM_PROMPTS) config.llm_alt_text_prompt = "Describe this image for a screen reader. Site languages: {languages}. Shown on: {urls}." config.llm_title_prompt = "Give this image a short title. Site languages: {languages}. Shown on: {urls}." end llm_api_url, llm_model and llm_api_key must all be set for the feature to activate (it's off by default). Once configured, uploading a new image queues a background job that sends it to the LLM once, asking for every enabled attribute (llm_generate_alt_text, llm_generate_title, both on by default) in the same request — the image itself is the bulk of the payload, so one call per attribute would upload it twice — and writes back a translation for every locale in LatoCms.config.locales. It only runs once, right after upload — it never overwrites text an admin later edits by hand. Generation is best effort: any failure (LLM unreachable, malformed response, ...) is logged and simply leaves the text as it was. Switching an attribute off leaves it out of both the post-upload run and the regenerate action. Each attribute has its own prompt, overridable with llm_alt_text_prompt / llm_title_prompt. Custom and default prompts can embed two placeholders, substituted on every call: {languages} — the configured locales, comma-separated (e.g. en, it). {urls} — the Frontend URLs of the pages currently using the media, comma-separated, so the model can look at where the image is actually shown. Pages without a frontend URL are skipped, and it reads none when the media isn't used anywhere yet (always the case for the automatic post-upload run — the context only pays off when regenerating). A prompt only needs to describe the task: the engine always appends its own response-format instruction (a JSON object keyed by attribute, then by locale), so a custom prompt can't break parsing. The task prompts of the enabled attributes travel together in that one request. A single Regenerate with AI button in the media edit form (shown only for images, and only when the LLM is configured) re-runs generation for every enabled attribute on demand, overwriting their current text in every locale — again in one call. Unlike the automatic post-upload run, this one is triggered by an admin waiting on it, so it runs as a Lato::Operation: the admin is taken to a live progress screen rather than the request blocking (and potentially timing out) on the LLM call. LLM features and prompt injection With an LLM configured, Lato CMS generates alt text and titles for images (automatically after upload and with Regenerate with AI) and offers Clone & translate for component text fields (string, textarea, text). Instructions are sent as the system message, and editor content is sent as delimited data (<data>...</data>) in the user message. Generated media texts are capped at 500 characters and translated text fields go through the rich text sanitizer. Residual risk: an LLM can still be steered by the content it reads, for example text inside an image or a field. Review generated alt text, titles and translations, and enable LLM features only with trusted editors. Images larger than llm_max_image_size are not sent to the LLM. Image sizes image and gallery fields can declare settings.sizes to generate resized variants via image_processing. Each size produces an Active Storage variant that is processed lazily on first request and exposed in the API under the attachment's sizes map. Each size accepts width, height, and a resize mode: limit (default): scale down to fit within the bounds, never upscale, keep aspect ratio. fit: scale to fit within the bounds, keep aspect ratio. fill: crop to exactly width×height. # config/lato_cms/components/hero.yml id: hero name: Hero fields: cover: name: Cover type: image settings: sizes: thumb: width: 150 height: 150 resize: fill medium: width: 800 The API response includes the generated variant URLs alongside the original: { "media_id": 12, "name": "cover.jpg", "alt_text": "A dog running on the beach", "title": "Dog on the beach", "filename": "cover.jpg", "url": "/rails/active_storage/blobs/.../cover.jpg", "sizes": { "thumb": "/rails/active_storage/representations/.../cover.jpg", "medium": "/rails/active_storage/representations/.../cover.jpg" } } Video poster After a video is uploaded to the media library, a background job generates a poster image from it via Active Storage previews (requires ffmpeg on the server) and attaches it to that media item — once per media item, regardless of how many fields or pages reuse it. From a page, the Actions → Translations menu lets you link the corresponding pages in the other configured locales. Linked pages form a translation group with at most one page per locale, and the link is symmetric: linking A to B makes both aware of each other. On the page view, the locale badge becomes a dropdown to jump to the same page in another language. When a page has linked translations, each component header shows a Clone dropdown. Picking a language copies that component's field values from the corresponding translation, replacing the current ones after confirmation; attachment fields keep referencing the same Media (not duplicated). When an LLM is configured, the dropdown also offers Clone & translate: same copy, but every string/textarea/text field is additionally translated into the target page's locale with one batched LLM call (HTML in text fields is preserved, only the visible text is translated). Everything else — select/multiselect/boolean/number/date/color/json/custom values, and media (including its alt text and title) — is left exactly as a plain clone would leave it: media alt text and title are translated independently by their own per-locale generation, not as part of cloning a page. The clone itself is instant, as always. Only the translation step — the actual LLM call — runs as a Lato::Operation (see the AI-generated alt text and title section above), landing the admin on a live progress screen instead of blocking the request. If the LLM call fails, the operation reports the failure, but the fields are still cloned (just untranslated) since that part already committed synchronously before the translation step ever started. Read a page's translations in the application or from the JSON API: page = LatoCms::Page.find_by(permalink: "/homepage") # Sibling pages in the other locales page.translations # => ActiveRecord::Relation of pages page.translation_for(:it) # => the linked Italian page, or nil # In as_json / API output, translations are exposed as a locale => page map: # { "it" => { id:, permalink:, frontend_url: }, ... } Public JSON API Exposure warning. The API is public and unauthenticated, keyed by sequential group ids, and has no draft or published state. Every page and media URL of every group is readable by anyone who can reach the endpoint, and signed blob URLs in redirect mode do not expire. group_id selects content; it is not an authorization token. Protect the endpoint at the host level (do not expose the route publicly, add a reverse proxy rule, or use Rack middleware and rate limiting) until per-group tokens and a publish state exist. GET /lato-cms/api/pages?group_id=ID&locale=xx GET /lato-cms/api/pages/:id_or_permalink?group_id=ID The first call lists pages without fields (locale is optional). The second returns one page with its fields. A missing group_id returns 400 and an unknown page returns 404. A page has id, title, permalink, locale, template_id, template_name, frontend_url (only http/https values are exposed, otherwise null), translations (locale => { id, permalink, frontend_url }), created_at and updated_at. The show response adds fields, keyed by template component id, with { component_id, name, fields }. Only enabled components are included. Regular component: fields is a hash of field_id => { id, field_id, field_type, field_name, required, value, attachments }. Repeater component: fields is an ordered array of { id, fields } items. Attachments: media_id, name, alt_text, title, filename, content_type, byte_size, url. Images and galleries add sizes, videos add poster_url. Sitemap export From the pages index, Actions → Export sitemap (CSV) runs an operation that produces a CSV with the columns locale, title, permalink and frontend_url for all pages of the current group. Cells starting with =, +, -, @, a tab or a carriage return are prefixed with an apostrophe to prevent formula injection. The export is rate limited (see Permissions). Accessibility notes Esc returns to the pages list only when no modal or dropdown is open and focus is not in a field. When there are unsaved component edits it asks for confirmation first. Leaving the editor with unsaved changes asks for confirmation. Media picker items and gallery reordering (move before / move after buttons) work with the keyboard.
