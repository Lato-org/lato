Configuration

Lato's configuration is managed by the Lato::Config class and can be customized through a dedicated initializer.
To override the default settings, create an initializer and add the following code: 

Lato.configure do |config|
  config.application_title = 'Lato example app'
  config.session_root_path = :tutorial_path
end

Application Configuration

Lato.configure do |config|
  config.application_title = 'Lato example app' # Application title
  config.application_version = '1.0.0' # Application version (default: '1.0.0')
  config.application_company_name = 'Lato Team' # Name of the owning company
  config.application_company_url = 'http://domain.com' # URL of the owning company
  config.application_brand_color = '#03256c' # Primary brand color used in navbar and UI elements (default: '#03256c')
end

Authentication Configuration

Lato.configure do |config|
  config.auth_disable_signup = true # Disable user self-signup
  config.auth_disable_recover_password = true # Disable password recovery
  config.auth_disable_web3 = true # Disable Web3 wallet login
  config.auth_disable_authenticator = true # Disable Google Authenticator login
  config.auth_disable_webauthn = true # Disable WebAuthn login
  config.auth_disable_signin_success_mail = true # Disable login notification email
  config.auth_recover_password_hourly_limit = 100 # Max password recovery emails sent per hour across all users, nil to disable (default: 100)
  config.auth_password_min_length = 8 # Minimum password length (default: 8)
end

auth_password_min_length is validated whenever a password is set (signup, invitation, password recovery and password change), and the signup and password forms display the requirement.

HCaptcha Configuration

HCaptcha is a service that helps protect websites from spam and abuse by using advanced risk analysis techniques. By integrating HCaptcha into your application, you can add an extra layer of security to authentication forms. When configured, it protects the signup and password recovery forms. 

Lato.configure do |config|
  config.hcaptcha_site_key = 'your-hcaptcha-site-key'
  config.hcaptcha_secret = 'your-hcaptcha-secret'
end

Requests Limit and Reverse Proxy

Authentication actions (signin, web3 signin, signup, password recovery, email verification, second factor) are limited per client IP and action. By default limit_requests(limit = 10, time_window = 10.minutes) allows exactly 10 requests per IP and action in each window; the 11th request receives an HTTP 429 response (message lato.too_many_requests). Signin also has a per-account limit: after 10 failed attempts in 15 minutes the email is blocked, from any IP, until the window passes. A successful signin resets the counter. Second factor (authenticator and WebAuthn) attempts are counted per user as well. Trade-off: an attacker who knows an email address can temporarily lock that account out of signin.

Shared cache required

Rate limits, password recovery codes, email verification codes and semaphores are stored in Rails.cache. Use a persistent cache shared across processes (Redis, Solid Cache, Memcached). With :null_store rate limits are disabled and password recovery never works; with :memory_store and multiple processes limits are per process. In production Lato logs a warning at boot if Rails.cache is a NullStore.

The client IP is read from request.remote_ip, so the application should run behind a reverse proxy (e.g. nginx, Kamal proxy, a load balancer) that appends the real client IP to the X-Forwarded-For header. Proxies on private networks are trusted by default; if your proxy uses a public IP, add it to the trusted proxies: 

# config/application.rb
config.action_dispatch.trusted_proxies = ActionDispatch::RemoteIp::TRUSTED_PROXIES + [IPAddr.new('203.0.113.10')]

Session Management Configuration

Lato.configure do |config|
  config.session_lifetime = 5.days # Absolute lifetime of the session cookie and of the session database record (default: 30 days)
  config.session_root_path = :tutorial_path # Path to redirect users after login/signup
end

session_lifetime is an absolute lifetime: it is not renewed on activity and there is no idle timeout. The session cookie is httponly, same_site: :lax, and secure only when the request is SSL, so set config.force_ssl = true in production.

Lato 3.25 requires Rails >= 8.1.3.1 and < 8.2. On upgrade, run rails lato:install:migrations and rails db:migrate before serving requests. Existing session cookies require a fresh sign-in.

Sessions use revocable database tokens. Signout revokes the current device. Password changes and recovery revoke every device; password recovery preserves existing second factors.

Sensitive account changes require the current password and an enrolled second factor. Authenticator enrollment requires a valid code before activation. Active authenticator secrets are not displayed. Enrollment continuations expire after five minutes.

Extensions must use session_update(extra_params) when changing session attributes so revocation and secure cookie options remain intact.

Email Configuration

Lato.configure do |config|
  config.email_from = 'demo@mail.com' # Sender email address for notifications
end

Note

The email_from setting can include a display name using the format "Name" <example@domain.com>.
Example: 

Lato.configure do |config|
  config.email_from = '"Company name" <demo@mail.com>'
end

Legal Information Configuration

Lato.configure do |config|
  config.legal_privacy_policy_url = 'https://domain.com/privacy' # Privacy policy URL
  config.legal_privacy_policy_version = 32 # Version number of the active privacy policy
  config.legal_terms_and_conditions_url = 'https://domain.com/terms' # Terms and conditions URL
  config.legal_terms_and_conditions_version = 32 # Version number of the active terms and conditions
end

Note

Lato tracks which version of the privacy policy and terms the user has accepted.
If the logged-in user has accepted a version lower than the one configured via legal_privacy_policy_version or legal_terms_and_conditions_version, a prompt will appear in the account management page to accept the new policies.

To check whether a user has accepted the latest policy versions, use the valid_accepted_privacy_policy_version? and valid_accepted_terms_and_conditions_version? methods on instances of the Lato::User model.
Example: 

user = Lato::User.all.first
throw "Privacy policy not accepted" unless user.valid_accepted_privacy_policy_version?
throw "Terms and conditions not accepted" unless user.valid_accepted_terms_and_conditions_version?

Account Connection Configuration

Lato.configure do |config|
  config.web3_connection = true # Allow users to link a Web3 wallet to their account
  config.authenticator_connection = true # Allow users to link Google Authenticator to their account
  config.webauthn_connection = true # Allow users to link WebAuthn to their account
  config.webauthn_origin = 'http://localhost:3000' # Origin URL for WebAuthn (must match the one used in your app)
  config.webauthn_rp_name = 'Lato Example App' # Relying Party name for WebAuthn
end

WebAuthn

webauthn_origin accepts a string or an array of origins. In production use HTTPS origins; the relying party id is derived from the origin. 

Lato.configure do |config|
  config.webauthn_origin = ['https://app.example.com', 'https://www.example.com']
end

The signature counter is persisted and a non-increasing counter is rejected to detect cloned authenticators. Limitations: each user can register one credential, there are no backup codes, and user verification is not required.

Authenticator (TOTP)

A code can be used only once (replay protection) and a drift of 15 seconds behind is accepted. The pending second factor step after the password expires after 10 minutes and is dropped after 5 wrong codes; the user must sign in again. The authenticator secret is stored in clear in the database, consider Active Record encryption for production.

Web3

Web3 requires the host application to add gem "eth" to its Gemfile; it is not a runtime dependency of Lato. The signed message is a text bound to host, purpose, nonce and issue time: 

example.com wants you to sign in with your Ethereum account.

URI: https://example.com
Nonce: ...
Issued At: ...

The nonce is single use and expires after 5 minutes. This is not a full SIWE (EIP-4361) implementation. Web3 signin pages require the user to be signed out. The browser loads ethers 5.7.2 from cdnjs with a dynamic import(): the version is pinned but without Subresource Integrity (import() cannot carry an integrity attribute). Applications that need strict supply-chain control should vendor the library.

Security

Web3 and email verification views use inline scripts, so a Content Security Policy needs unsafe-inline or nonces for those pages. See the "Production security checklist" in the README for the full list (force SSL, shared cache, session lifetime, cleaner jobs, invitations, secrets at rest).
