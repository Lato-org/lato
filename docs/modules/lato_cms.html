Lato CMS

Source: https://raw.githubusercontent.com/Lato-org/lato_cms/refs/heads/main/test/dummy/app/views/application/documentation.html.erb

How to use Lato CMS

lato_cms adds content management to a Lato admin panel. Use it when admins need to create pages and edit structured content without changing application code. Lato CMS works with Lato Spaces, so pages can be scoped to the selected group.

Installation

Requires Rails 8.1.3.1 or newer in the 8.1 series and Lato 3.25.0 or newer. Existing applications must run rails lato:install:migrations and rails db:migrate before deployment. Previous sessions are invalidated.

Add Lato CMS to the application Gemfile:

gem "lato"
gem "lato_spaces"
gem "lato_cms"

Install the engines and run migrations:

bundle
rails lato_spaces:install:application
rails lato_spaces:install:migrations
rails lato_cms:install:application
rails lato_cms:install:migrations
rails db:migrate

lato_cms:install:application writes an example template and component into config.templates_path.

Mount both engines in config/routes.rb:

Rails.application.routes.draw do
  mount LatoSpaces::Engine => "/lato-spaces"
  mount LatoCms::Engine => "/lato-cms"

  # ...
end

Lato CMS requires a selected Lato Spaces group: every CMS controller calls authenticate_group, and pages and media are scoped to the selected group. Create a group and select it before using the CMS.

Import styles in app/assets/stylesheets/application.scss:

@import "lato_cms/application";

Import JavaScript in app/javascript/application.js:

import "lato_cms/application"

Permissions

Users must be logged into Lato, must have a selected Lato Spaces group, and must have a Lato CMS role. The role is stored in the lato_cms_admin_role column of Lato::User and the available roles come from config.admin_roles (default { none: 0, operator: 1, admin: 2 }).

Role Can
operator (1) Access the CMS, edit page fields, enable or disable components, clone components (including Clone & translate when an LLM is configured), upload media and edit its metadata, Regenerate with AI, export the sitemap.
admin (2) Everything an operator can do, plus create and update page settings (title, permalink, frontend URL, template), delete pages, manage translation links, replace media files, and delete media. 
user = Lato::User.find_by(email: "admin@example.com")
user.update!(lato_cms_admin_role: 2)

Expensive operations (sitemap export, clone component, regenerate media text) are rate limited to 10 requests per user per minute. The counter lives in Rails.cache: a memory store limits each process separately and a null store disables the limit.

Configuration

LatoCms.configure do |config|
  config.locales = [:en, :it]
  config.templates_path = "config/lato_cms"
  config.media_url_mode = :redirect
  config.media_max_file_size = 50.megabytes
end
Option Default Description
locales [:en] Locales available for pages and for media alt text and title.
templates_path "config/lato_cms" Templates are read from <path>/templates/*.yml, components from <path>/components/*.yml.
admin_roles { none: 0, operator: 1, admin: 2 } Role map for lato_cms_admin_role. See Permissions.
media_url_mode :redirect :redirect or :proxy. See the README for when to use :proxy.
media_allowed_content_types LatoCms::Config::DEFAULT_MEDIA_ALLOWED_CONTENT_TYPES Allowed upload content types. A trailing * matches any subtype and nil allows everything. Checked on the server against the content type Active Storage identifies. The default list is image/*, video/*, audio/*, application/pdf, text/plain, text/csv, application/zip, legacy Word/Excel/PowerPoint types, application/vnd.openxmlformats-officedocument.* and application/vnd.oasis.opendocument.*. HTML is excluded on purpose.
media_max_file_size 100.megabytes Maximum upload size. nil means no limit.
llm_api_url, llm_model, llm_api_key nil OpenAI-compatible endpoint. All three are required to enable LLM features. An http URL to a non-local host logs a warning, because the API key travels in clear.
llm_generate_alt_text, llm_generate_title true Which media attributes the LLM generates.
llm_alt_text_prompt, llm_title_prompt nil Custom prompts. Placeholders: {languages}, {urls}.
llm_max_image_size 20.megabytes Larger images are not sent to the LLM, because the whole file is read in memory and base64-encoded.

Uploaded SVG and HTML files are served as attachments thanks to the Active Storage defaults (content_types_to_serve_as_binary). Lato CMS relies on this: do not change those defaults.

Templates and components

Templates define which content blocks are available on a page. Components define the fields inside those blocks. Both are YAML files stored in the application. Template components are enabled by default, and each page can turn optional components on or off from the admin panel. 

config/lato_cms/
  templates/
    homepage.yml
    blog_post.yml
  components/
    hero.yml
    content.yml

Generate new files with Rails tasks:

rails "lato_cms:generate:template[blog_post]"
rails "lato_cms:generate:component[hero,title:string,subtitle:textarea,image:image]"
rails "lato_cms:generate:custom_field[icon_note]"

The component generator accepts every built-in field type (including image, video and gallery) and aborts with an error on an unsupported one. It does not accept custom, which needs a render path: use the custom field generator instead (see Custom fields).

Template example

A template component accepts component_id, name, required: true (the component cannot be disabled) and repeater: true (alias repeatable) with settings.min and settings.max item counts. 

# config/lato_cms/templates/homepage.yml
id: homepage
name: Homepage
components:
  hero_section:
    component_id: hero
    name: Hero Section
    required: true
  content_section:
    component_id: content

Optional and required components

Components listed in a template are optional unless required: true is set. Optional components show an enabled switch in the page editor. Admins can disable them for a specific page without removing the component from the template. 

# config/lato_cms/templates/homepage.yml
id: homepage
name: Homepage
components:
  hero_section:
    component_id: hero
    name: Hero Section
    required: true
  banner_section:
    component_id: banner
    name: Promotional Banner
  content_section:
    component_id: content
    name: Content

In this example hero_section is always active and cannot be disabled. banner_section and content_section can be enabled or disabled per page. Disabled components are hidden in the editor, cannot be saved, and are not exposed when page fields are returned by the API.

Repeater components

Add repeater: true to a template component when admins need to create multiple items with the same field set. The API returns repeater fields as an ordered array of items. 

# config/lato_cms/templates/homepage.yml
components:
  feature_cards:
    component_id: feature_card
    name: Feature Cards
    repeater: true
    settings:
      min: 1
# config/lato_cms/components/feature_card.yml
id: feature_card
name: Feature Card
fields:
  title:
    name: Title
    type: string
    required: true
  description:
    name: Description
    type: textarea

Component example

# config/lato_cms/components/hero.yml
id: hero
name: Hero
fields:
  title:
    name: Title
    type: string
    required: true
  subtitle:
    name: Subtitle
    type: textarea
  image:
    name: Image
    type: image
  attachments:
    name: Attachments
    type: file
    settings:
      multiple: true

Any field can declare required: true. For attachment fields (file, image, video, gallery) this means the field must keep at least one file: the editor blocks saving when the field would end up empty, and the server rejects the save with an error otherwise.

Server-side validation

  • required is enforced for scalar fields: a blank value is refused.
  • select and multiselect values must be among the declared options.
  • number values must be numeric, color values must be #rgb or #rrggbb, date and datetime values must parse.
  • An untouched color field is saved empty (not #000000), and a non-required color can be cleared.
  • Field types are resolved from the template and component YAML on the server; the component id sent by the browser is ignored. Saving a template component or a field that is not in the page template is refused (422).
  • Changing the template of a page hides the fields saved under the old one. The page settings form warns about it.

text HTML is sanitized on save and on output with an allowlist of tags (LatoCms::PageField::RICH_TEXT_TAGS) and attributes (RICH_TEXT_ATTRIBUTES). The style attribute is reduced to text-align.

Media library

file, image, video, and gallery fields don't upload straight into the field: admins pick from a shared Media library (Media in the sidebar), scoped to the current Lato Spaces group like pages. Each field opens a picker overlay to search the existing library or drag & drop a new file; the same media item can be reused across any number of fields and pages.

A media item's name, alt text and title are edited from the library's own edit form, not from the upload dialog — on upload, name defaults to the filename. Uploads are checked on the server against media_allowed_content_types and media_max_file_size (see Configuration). Deleting a media item still referenced by a field is refused until it's removed from every field using it. An admin can force the deletion (the delete endpoint accepts force=true): the media is then removed from every field that used it.

Uploads (from the library and from the picker's Upload new tab alike) show a progress bar with the real upload percentage, so large videos don't look like a frozen page.

Where a media item is used

The library index shows how many page fields reference each media item, and filters list only the unused ones (the only ones that can be deleted without force) or those still missing an alt text or a title in at least one configured locale (alt text only applies to images; a title is editable on any media type). Each media item also has a detail page: a read-only summary (preview, name, alt text and title per locale) plus the list of pages using it, with a link to each one and the fields involved.

Replacing a file

The edit form of a media item has a second tab, Replace file (admins only): it uploads a new file over the existing media item, keeping the same record, so every page and field already referencing it shows the new file. That's the point of the action — swapping a logo everywhere at once — and its danger, which is why the form states how many fields are affected and asks for a confirmation. The previous file is deleted, and media_type is re-inferred from the new one. Metadata (name, alt text, title) is kept: to change it, use the Details tab. Uploading a file from the library's Upload action, as before, always creates a separate media item instead.

Alt text and title are translatable: alt text is only shown for image media, title for every media type, and the edit form has one tab per locale configured in LatoCms.config.locales for each. Each locale's text is independent — leaving one blank doesn't affect the others. 

image = LatoCms::Media.find(12)
image.alt_text(:en)              # => "A dog running on the beach"
image.alt_text(:it)               # => nil, if the Italian tab was left blank
image.alt_text_translations       # => { "en" => "A dog running on the beach" }
image.title(:en)                  # => "Dog on the beach"
image.title_translations          # => { "en" => "Dog on the beach", "it" => "Cane in spiaggia" }

image.alt_text / image.title without an explicit locale resolve against I18n.locale. When a media item is read off a page's field (page_field.attachments in the JSON API, as alt_text and title), both resolve against that page's own locale instead, so a multi-locale API response always gets the right language regardless of the server's current I18n.locale.

AI-generated alt text and title

Configure an OpenAI-compatible endpoint to have alt text and title generated automatically: 

LatoCms.configure do |config|
  config.llm_api_url = "https://api.openai.com/v1"
  config.llm_model = "gpt-4o-mini"
  config.llm_api_key = Rails.application.credentials.dig(:openai, :api_key)

  # Optional, both default to true once the LLM is configured
  config.llm_generate_alt_text = true
  config.llm_generate_title = false

  # Optional custom prompts (nil = built-in defaults, see LatoCms::Config::DEFAULT_LLM_PROMPTS)
  config.llm_alt_text_prompt = "Describe this image for a screen reader. Site languages: {languages}. Shown on: {urls}."
  config.llm_title_prompt = "Give this image a short title. Site languages: {languages}. Shown on: {urls}."
end

llm_api_url, llm_model and llm_api_key must all be set for the feature to activate (it's off by default). Once configured, uploading a new image queues a background job that sends it to the LLM once, asking for every enabled attribute (llm_generate_alt_text, llm_generate_title, both on by default) in the same request — the image itself is the bulk of the payload, so one call per attribute would upload it twice — and writes back a translation for every locale in LatoCms.config.locales. It only runs once, right after upload — it never overwrites text an admin later edits by hand. Generation is best effort: any failure (LLM unreachable, malformed response, ...) is logged and simply leaves the text as it was. Switching an attribute off leaves it out of both the post-upload run and the regenerate action.

Each attribute has its own prompt, overridable with llm_alt_text_prompt / llm_title_prompt. Custom and default prompts can embed two placeholders, substituted on every call:

  • {languages} — the configured locales, comma-separated (e.g. en, it).
  • {urls} — the Frontend URLs of the pages currently using the media, comma-separated, so the model can look at where the image is actually shown. Pages without a frontend URL are skipped, and it reads none when the media isn't used anywhere yet (always the case for the automatic post-upload run — the context only pays off when regenerating).

A prompt only needs to describe the task: the engine always appends its own response-format instruction (a JSON object keyed by attribute, then by locale), so a custom prompt can't break parsing. The task prompts of the enabled attributes travel together in that one request.

A single Regenerate with AI button in the media edit form (shown only for images, and only when the LLM is configured) re-runs generation for every enabled attribute on demand, overwriting their current text in every locale — again in one call. Unlike the automatic post-upload run, this one is triggered by an admin waiting on it, so it runs as a Lato::Operation: the admin is taken to a live progress screen rather than the request blocking (and potentially timing out) on the LLM call.

LLM features and prompt injection

With an LLM configured, Lato CMS generates alt text and titles for images (automatically after upload and with Regenerate with AI) and offers Clone & translate for component text fields (string, textarea, text). Instructions are sent as the system message, and editor content is sent as delimited data (<data>...</data>) in the user message. Generated media texts are capped at 500 characters and translated text fields go through the rich text sanitizer.

Residual risk: an LLM can still be steered by the content it reads, for example text inside an image or a field. Review generated alt text, titles and translations, and enable LLM features only with trusted editors. Images larger than llm_max_image_size are not sent to the LLM.

Image sizes

image and gallery fields can declare settings.sizes to generate resized variants via image_processing. Each size produces an Active Storage variant that is processed lazily on first request and exposed in the API under the attachment's sizes map.

Each size accepts width, height, and a resize mode:

  • limit (default): scale down to fit within the bounds, never upscale, keep aspect ratio.
  • fit: scale to fit within the bounds, keep aspect ratio.
  • fill: crop to exactly width×height.
# config/lato_cms/components/hero.yml
id: hero
name: Hero
fields:
  cover:
    name: Cover
    type: image
    settings:
      sizes:
        thumb:
          width: 150
          height: 150
          resize: fill
        medium:
          width: 800

The API response includes the generated variant URLs alongside the original:

{
  "media_id": 12,
  "name": "cover.jpg",
  "alt_text": "A dog running on the beach",
  "title": "Dog on the beach",
  "filename": "cover.jpg",
  "url": "/rails/active_storage/blobs/.../cover.jpg",
  "sizes": {
    "thumb": "/rails/active_storage/representations/.../cover.jpg",
    "medium": "/rails/active_storage/representations/.../cover.jpg"
  }
}

Video poster

After a video is uploaded to the media library, a background job generates a poster image from it via Active Storage previews (requires ffmpeg on the server) and attaches it to that media item — once per media item, regardless of how many fields or pages reuse it. Poster generation is best effort: when ffmpeg is unavailable or preview fails, the upload still succeeds and the video is exposed without a poster. 

# config/lato_cms/components/hero.yml
id: hero
name: Hero
fields:
  trailer:
    name: Trailer
    type: video

The API response exposes the video attachment with its poster URL (null until the job runs):

{
  "media_id": 12,
  "name": "trailer.mp4",
  "alt_text": null,
  "title": "Product trailer",
  "filename": "trailer.mp4",
  "content_type": "video/mp4",
  "byte_size": 1048576,
  "url": "/rails/active_storage/blobs/.../trailer.mp4",
  "poster_url": "/rails/active_storage/blobs/.../trailer_poster.jpg"
}

Custom fields

Use type: custom when a component needs an editor that is not covered by built-in field types. Generate a partial in the host application: 

rails "lato_cms:generate:custom_field[icon_note]"

This creates app/views/lato_cms/custom_fields/_icon_note.html.erb. Reference it with render in the component: 

# config/lato_cms/components/hero.yml
id: hero
name: Hero
fields:
  icon_note:
    name: Icon note
    type: custom
    render: lato_cms/custom_fields/icon_note
    required: false
    settings:
      placeholder: "Example: rocket|Hero launch section"

The partial receives the locals field_id, field_config, page_field, input_name_prefix, dom_id_prefix and persisted_field_id. Build input names and ids with the helpers lato_cms_field_input_name and lato_cms_field_dom_id, so the field also works inside repeaters, where both carry an item prefix: 

<%# app/views/lato_cms/custom_fields/_icon_note.html.erb %>
<% settings = field_config["settings"] || {} %>
<% current_value = page_field&.value.to_s %>
<% input_name = lato_cms_field_input_name(field_id, input_name_prefix: local_assigns[:input_name_prefix]) %>
<% input_id = lato_cms_field_dom_id(field_id, dom_id_prefix: local_assigns[:dom_id_prefix]) %>

<label class="form-label" for="<%= input_id %>">
  <%= field_config["name"] || field_id.humanize %>
</label>

<input type="text"
  class="form-control"
  name="<%= input_name %>"
  id="<%= input_id %>"
  value="<%= current_value %>"
  placeholder="<%= settings["placeholder"] %>">

Custom field values are saved like standard scalar fields. Use settings for custom options consumed by the partial.

Using CMS content in the application

Use Lato CMS pages as structured content records for public or private pages. Field values are available in their parsed form, so numbers, booleans, dates, JSON values, multi-select values, and files can be consumed directly by application views or serializers.

Scope pages by group and pick fields by template component, because the same field id can exist in several components. 

page = LatoCms::Page.for_lato_spaces_group(group_id).find_by!(permalink: "/home")
title = page.fields.find_by(template_component_id: "hero_section", field_id: "title")&.parsed_value
image = page.fields.find_by(template_component_id: "hero_section", field_id: "image")&.media&.first
image_url = image&.url

# Or the whole page, as served by the JSON API
page.as_json(include_fields: true)

Page translations

Each page belongs to a single locale. From a page, the Actions → Translations menu lets you link the corresponding pages in the other configured locales. Linked pages form a translation group with at most one page per locale, and the link is symmetric: linking A to B makes both aware of each other. On the page view, the locale badge becomes a dropdown to jump to the same page in another language.

When a page has linked translations, each component header shows a Clone dropdown. Picking a language copies that component's field values from the corresponding translation, replacing the current ones after confirmation; attachment fields keep referencing the same Media (not duplicated).

When an LLM is configured, the dropdown also offers Clone & translate: same copy, but every string/textarea/text field is additionally translated into the target page's locale with one batched LLM call (HTML in text fields is preserved, only the visible text is translated). Everything else — select/multiselect/boolean/number/date/color/json/custom values, and media (including its alt text and title) — is left exactly as a plain clone would leave it: media alt text and title are translated independently by their own per-locale generation, not as part of cloning a page.

The clone itself is instant, as always. Only the translation step — the actual LLM call — runs as a Lato::Operation (see the AI-generated alt text and title section above), landing the admin on a live progress screen instead of blocking the request. If the LLM call fails, the operation reports the failure, but the fields are still cloned (just untranslated) since that part already committed synchronously before the translation step ever started.

Read a page's translations in the application or from the JSON API:

page = LatoCms::Page.find_by(permalink: "/homepage")

# Sibling pages in the other locales
page.translations               # => ActiveRecord::Relation of pages
page.translation_for(:it)       # => the linked Italian page, or nil

# In as_json / API output, translations are exposed as a locale => page map:
# { "it" => { id:, permalink:, frontend_url: }, ... }

Public JSON API

Exposure warning. The API is public and unauthenticated, keyed by sequential group ids, and has no draft or published state. Every page and media URL of every group is readable by anyone who can reach the endpoint, and signed blob URLs in redirect mode do not expire. group_id selects content; it is not an authorization token. Protect the endpoint at the host level (do not expose the route publicly, add a reverse proxy rule, or use Rack middleware and rate limiting) until per-group tokens and a publish state exist. 
GET /lato-cms/api/pages?group_id=ID&locale=xx
GET /lato-cms/api/pages/:id_or_permalink?group_id=ID

The first call lists pages without fields (locale is optional). The second returns one page with its fields. A missing group_id returns 400 and an unknown page returns 404.

A page has id, title, permalink, locale, template_id, template_name, frontend_url (only http/https values are exposed, otherwise null), translations (locale => { id, permalink, frontend_url }), created_at and updated_at. The show response adds fields, keyed by template component id, with { component_id, name, fields }. Only enabled components are included.

  • Regular component: fields is a hash of field_id => { id, field_id, field_type, field_name, required, value, attachments }.
  • Repeater component: fields is an ordered array of { id, fields } items.
  • Attachments: media_id, name, alt_text, title, filename, content_type, byte_size, url. Images and galleries add sizes, videos add poster_url.

Sitemap export

From the pages index, Actions → Export sitemap (CSV) runs an operation that produces a CSV with the columns locale, title, permalink and frontend_url for all pages of the current group. Cells starting with =, +, -, @, a tab or a carriage return are prefixed with an apostrophe to prevent formula injection. The export is rate limited (see Permissions).

Accessibility notes

  • Esc returns to the pages list only when no modal or dropdown is open and focus is not in a field. When there are unsaved component edits it asks for confirmation first.
  • Leaving the editor with unsaved changes asks for confirmation.
  • Media picker items and gallery reordering (move before / move after buttons) work with the keyboard.
